# Deployment

Last updated: 2026-11-17

This document covers deploying Interchange: required environment variables, setting up Neon, deploying to Vercel, running migrations and the seed, the automated deploy job and hourly health workflow in GitHub Actions, and the steps to activate the platform for a real project once it is deployed.

## Environment variables

Copy `.env.example` to `.env.local` for local development, and set the same values in your Vercel project's environment variables for each deploy target (Preview / Production).

| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_URL` | Yes | Neon Postgres pooled connection string. The platform's own database (see the two-database model in `docs/architecture.md`). |
| `CREDENTIAL_MASTER_KEY` | Yes | 64 hex characters (32 bytes). AES-256-GCM master key used to encrypt outbound partner credentials at rest. It also encrypts the queued payloads of async (202) inbound calls, through a separate derived key, for at most 24 hours each. Generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Never prefix with `NEXT_PUBLIC_`; it must never reach the client. |
| `CREDENTIAL_MASTER_KEY_PREVIOUS` | No | Prior 64-hex master key (key version 0). Set it to the old value when you rotate: a blob that fails to decrypt under the current key is then tried under this one (`core/crypto/vault.ts:116-133`), and `npm run rekey` moves the blobs to the current key (`scripts/rekey.ts:1-37`). Unset it after the re-key. See "Master-key rotation" below and the operations runbook, section 3 (in the source repository). |
| `NEXTAUTH_SECRET` | Yes | next-auth session secret. Generate with `openssl rand -base64 32`. |
| `NEXTAUTH_URL` | Yes | The deployed app's public URL (for example `https://your-project.vercel.app`). Also used as a fallback base URL for building the QStash tick callback if `APP_URL` is not set. |
| `APP_URL` | No | Public base URL QStash should call (`<APP_URL>/api/jobs/tick`). Falls back to `NEXTAUTH_URL`. |
| `QSTASH_TOKEN` | No | Upstash QStash token, used only to register or delete the one platform tick schedule (`armTick()` / `disarmTick()`). Leave unset for a dormant deploy: nothing can be armed. |
| `QSTASH_TICK_CRON` | No | Cadence of the single platform tick (default `*/5 * * * *`, UTC). Job schedules are evaluated by the tick, so none can run more often than this. Takes effect when the tick is (re-)armed. |
| `ACTIVITY_RETENTION_DAYS` | No | Fallback only: `activity_log` retention in days (default `30`) when no `retention` row exists in `app_setting`. The row (`{enabled, activityDays, jobDays}`, days 1 to 365; `jobDays` defaults to 30 and covers jobs, step logs and process runs, and a stored row without it reads 30) is edited from the Activity log screen and wins over this variable; `enabled: false` stops every automatic delete. Pruning runs from the tick and from a throttled trigger after inbound requests, so a deployment with the tick dormant prunes only after traffic. P3a adds no new environment variable, and neither does P3b. |
| `QSTASH_CURRENT_SIGNING_KEY` / `QSTASH_NEXT_SIGNING_KEY` | Yes, to use any `/api/jobs/*` route | QStash request-signing keys. `/api/jobs/tick`, `/dispatch` and `/process` verify the `Upstash-Signature` header with them and **fail closed**: with either key unset they return 503. Set both (from the QStash console) before arming. |
| `QSTASH_DEV_BYPASS` | No | Set to `1` to let the job endpoints run unsigned for local testing. Honoured only when `NODE_ENV` is not `production`; it does nothing in production. |
| `JOB_STUCK_MINUTES` | No | A job left `PROCESSING` longer than this (default `10`) is reclaimed by the tick: an outbound job goes back to `RETRY` with backoff, or to the DLQ when attempts are exhausted; an async (202) inbound job does the same, with code `RECLAIMED`; an inline inbound job goes to `FAILED` and is not re-executed. Outbound handlers and connectors that set `asyncInbound` must therefore be idempotent. The same value sets the Stuck card threshold on the Queue page (P4d), so the card counts what the next reclaim would take. |
| `RATE_LIMIT_IP_RPM` | No | Per-client-IP inbound request limit per minute (default `250`). The per-system limit is `external_system.rate_limit_rpm`, set per system. |
| `ADMIN_RATE_LIMIT_IP_RPM` | No | Per-client-IP request limit per minute for `/api/admin/*` (default `300`), checked before sign-in state. Only sound behind Vercel or a trusted proxy that overwrites the forwarded-IP headers (see `docs/security.md`). |
| `ADMIN_RATE_LIMIT_USER_RPM` | No | Per-user request limit per minute for `/api/admin/*` (default `120`), checked after authorization. |
| `CORS_ALLOWED_ORIGINS` | No | Comma-separated exact origins. It is the allowlist for cross-origin calls to `/api/*` except inbound; unset or empty allows none, and `*` is ignored. `/api/inbound/*` uses each system's own origin list (edited on its CORS tab), and when this variable is set it acts as a ceiling there: an origin must be in both lists. It never applies to `/api/admin/*`. |
| `CREDENTIALS_REVEAL_ENABLED` | No | Set to exactly `1` to let users holding `credentials:reveal` decrypt a stored outbound credential. Unset means reveal is off, which is the intended default. |
| `CREDENTIALS_REVEAL_LIMIT` | No | Reveals allowed per user per 10 minutes when reveal is enabled (default `10`). |
| `SEED_ADMIN_EMAIL` | No | Email of the admin user created by `npm run db:seed` (default `admin@interchange.local`). |
| `SEED_ADMIN_PASSWORD` | **Required unless the database is local** | Password for the seeded admin. The seed throws if it is unset in production, and also whenever `DATABASE_URL` does not point at `localhost` / `127.0.0.1`, regardless of `NODE_ENV`. |
| `SEED_ALLOW_DEFAULT` | No | Set to exactly `1` to let the seed use the published development default password against a non-local database. Do not set it for anything reachable. |

A dormant deploy needs only `DATABASE_URL`, `CREDENTIAL_MASTER_KEY`, and `NEXTAUTH_SECRET` / `NEXTAUTH_URL` to boot and serve the admin console. The QStash keys are needed only once you want the job endpoints to answer.

`ADMIN_RATE_LIMIT_IP_RPM`, `ADMIN_RATE_LIMIT_USER_RPM`, `CORS_ALLOWED_ORIGINS`, `CREDENTIALS_REVEAL_ENABLED` and `CREDENTIALS_REVEAL_LIMIT` are optional and safe when unset (default limits, an empty env CORS list, reveal off). Leave them unset on Vercel unless you have a specific need; unset is the intended production posture. With `CORS_ALLOWED_ORIGINS` unset, inbound browser access is still possible, but only for origins an operator has added to a specific system's own CORS list.

**P4d (Queue page and file upload) adds no environment key, secret, dependency or migration.** The Queue page reads `JOB_STUCK_MINUTES` and the existing QStash signing keys (presence only), and a file sent from the Run drawer rides in the job payload through the existing `jobs.run`. Rolling back is a redeploy.

**Service tokens.** They need no environment variable. Service keys are issued per system in the console (the system's Credentials tab, "Issue service key", for a system of a `partner+service` type), and the key is encrypted under the existing `CREDENTIAL_MASTER_KEY`. Callers mint tokens of at most 900 seconds; for testing, the repository script does it:

```
SERVICE_KEY=<plaintext> npm run mint:service-token -- --kid <kid> --sub worker-1 --sys ACME-ERP --ttl 300
```

It prints only the token, to be sent as `X-Service-Token` next to the partner credential. `--kid` (the key id shown with the key) and `--sys` (the system code) are required, `--ttl` is 1 to 900 (default 300). `SERVICE_KEY` is a shell variable of the person running the script, not a deployment environment key. Each key can be rotated with a grace window and revoked on the same tab; see `docs/security.md`.

**Master-key rotation.** To rotate `CREDENTIAL_MASTER_KEY`, move the old value to `CREDENTIAL_MASTER_KEY_PREVIOUS` and set the new one. Every blob records a `keyVersion`, but every writer stamps 1, so the version is a slot name and not a key identity (`core/crypto/vault.ts:37-55`). Decrypt reads with the key the blob names; only when that key's authentication tag fails, and only when the other slot is set and holds a different key, it tries the other slot once with the same purpose and AAD (`core/crypto/vault.ts:116-133`). A missing key, a wrong AAD or purpose, tampered bytes and a previous key equal to the current key still fail. So the env flip (old value into `CREDENTIAL_MASTER_KEY_PREVIOUS`, new value into `CREDENTIAL_MASTER_KEY`) causes no outage, and `npm run rekey` (a dry run; `-- --apply` writes) then re-encrypts every stored secret under the current key: outbound credentials, type defaults, storage and SFTP secrets, certificate keys, service keys and queued async payloads (`scripts/rekey.ts:1-37`, `scripts/rekey.ts:106-128`). After a clean re-run, unset `CREDENTIAL_MASTER_KEY_PREVIOUS` and redeploy so the retired key stops opening blobs. The Basic username lookup cannot be re-keyed (the username is stored only as a salted hash), so `--apply` clears it and each Basic credential is re-indexed the next time it authenticates on its own system (`scripts/rekey.ts:327-335`, `core/auth/with-partner-auth.ts:308-317`); until then a live Basic credential presented to the wrong system answers 401 instead of 403, and one never used before the previous key is unset is not found (401) until it is reissued. Follow the operations runbook, section 3 (in the source repository) for the full procedure.

## Neon setup

1. Create a Neon project (https://neon.tech). Neon's serverless Postgres is what makes this stack work well on Vercel: connections are pooled over WebSocket rather than long-lived TCP, which matches serverless function lifecycles.
2. Copy the pooled connection string (Neon dashboard shows both a direct and a pooled variant; use the pooled one, it ends in `-pooler` in the host) into `DATABASE_URL`.
3. No manual schema setup is needed beyond running migrations (next section). `core/db.ts` and `db/migrate.ts` both connect through `@neondatabase/serverless`'s `Pool`, which is what `drizzle-orm/neon-serverless` expects.

## Vercel deploy

1. Import the repository into Vercel as a Next.js project. Framework detection is automatic for Next.js 16.
2. Set the environment variables from the table above in the Vercel project settings, for whichever environments you deploy (Production, and Preview if you want preview deploys to also work end to end).
3. Vercel runs `npm run build`, which is wired to `prebuild` in `package.json`:

   ```
   "prebuild": "npm run generate:connectors && npm run generate:openapi",
   "build": "next build",
   ```

   This means every deploy regenerates `src/connectors/generated/manifest.ts` and `src/connectors/generated/catalog.ts` (each connector's JSON Schema and sample) from whatever connector folders exist in the repository at that commit, then `src/generated/openapi.json` from the catalog, before Next.js builds. The build fails if a connector's `sample` does not pass its input schema. You do not need a separate manual step to keep them in sync; committing a new connector folder and pushing is enough, though committing the generated files too (as the repository does) keeps them visible in code review.
4. `ssh2` (used by the SFTP connection test) is listed in `serverExternalPackages` in `next.config.ts`, so the bundler leaves it alone. It has optional native dependencies (`cpu-features`, built with `nan`); npm tolerates their failing to compile, and `ssh2` falls back to pure JavaScript, so the install and the build succeed either way. If `ssh2` cannot load at runtime, only the SFTP test reports "ssh client unavailable"; the rest of the admin API is unaffected. P2c adds no environment variable: the certificate and SFTP features use the existing `CREDENTIAL_MASTER_KEY`, and the SFTP test rate limits are constants.
5. `vercel.json` pins the functions to one region, `sin1`, next to the database. Set it to the Vercel region closest to your Neon project's region: a request makes several sequential database round trips (about 15 on an inbound call), and each one costs about 200 ms when the database is on another continent. `/api/health` reports the time of its probe query as `Server-Timing: db;dur=<ms>` (`src/app/api/health/route.ts:31`); a few milliseconds means the two are co-located. On 2026-11-16 the median of 20 reads was 218 ms from `iad1` and 3 ms from `sin1`. No further Vercel-specific configuration is required. Route handlers run on the default Node.js runtime (not Edge), which is what the auth guard and Drizzle client need.

## Migration and seed steps

Run these once against a fresh `DATABASE_URL`, whether that is a local Neon branch or the production database:

```
npm run db:migrate
```

This runs `db/migrate.ts`, which applies every migration file under `db/migrations/` via `drizzle-orm`'s Neon migrator. It loads `.env.local` automatically in local dev (`tsx --env-file=.env.local`); on a deploy host, ensure `DATABASE_URL` is present in the environment instead. The GitHub Actions workflow (`.github/workflows/ci.yml`) does not run migrations against a real database: it runs the generators, typecheck, lint, `audit:log-calls`, the tests, a build and the `/demo` smoke walk, and the tests apply the migrations to an in-memory Postgres (pglite). Its `deploy` job (P7b) runs after those checks on a push to `main` and still does not migrate: it refuses to deploy a push that changes `db/migrations/` unless the head commit message says the migration was applied by hand (see "Automated deploy and the Health workflow (P7b)" below).

**Migration `0002_p2a_credentials.sql` must be applied before deploying this version.** The gateway and the credential services read columns it adds (`lookup_hash`, `expires_at`, `rotated_to_id`, `username_lookup`, `system_credential.revoked_at` and a required `label`). It backfills missing labels, renames older duplicate active labels by appending `-<first 8 characters of the row id>` (the newest row keeps the label), drops the one-Basic-row-per-system index, and adds the partial unique indexes. Existing API keys, bearer tokens and Basic credentials keep working: they are verified by a fallback scoped to their own system and indexed on first use.

**Migration `0003_p2b_registry.sql` must be applied before deploying this version.** The gateway and the registry services read what it adds: `external_system.deleted_at`, `health_url`, `health_status`, `health_reason`, `health_checked_at` and `cors_origins`; `integration_type.auth_policy` (default `partner`) and `deleted_at`; `endpoint_config.updated_at` plus a unique index so a system has at most one endpoint config; and the new `endpoint_rate_limit` table. Existing rows take the defaults, so nothing changes for them except that SUSPENDED systems now stop firing schedules and hold their queued jobs (see `docs/architecture.md`).

**Migration `0004_p2c_certs_sftp.sql` must be applied before deploying this version.** It adds the `system_certificate` table and reshapes `sftp_config` (the old password columns and `remote_path` are dropped; `auth_method`, an encrypted `enc_secret_*` blob, `host_key_sha256`, `paths` and `updated_at` are added, with a unique index so a system has at most one config). Dropping columns is only safe on an empty table, so the migration begins with a guard that raises an error if `sftp_config` has any row; a database with SFTP data fails safe instead of losing it. The old code never reads the table, so migrate first, then deploy. Its last statement adds `certificates:write`, `sftp:write` and `sftp:test` to the `operator` role once. It is idempotent (a re-run gives the same sorted list), never touches `admin` or `viewer`, and does nothing if no `operator` row exists.

**Migration `0009_p4b_credentials.sql` must be applied before deploying this version.** The credential resolver and the credential services read what it adds: the `type_credential` table (default credentials of an integration type); `credential_version` (integer, default 0) on `external_system` and `integration_type`; `endpoint_config.auth_label` and `auth_header` (nullable); and `system_credential.allowed_origins` (a text array, default empty). It also adds the partial index `job_claim_due_idx` on the job claim order. It is additive and guarded: every statement uses `IF NOT EXISTS`, and the foreign key is added inside a `DO` block that checks `pg_constraint` first, so a re-run is harmless. Existing endpoints have no auth label, so none of them starts sending a credential by itself.

**Migration `0011_p4c_job_list_idx.sql` adds one index, `job_created_idx` on `job`.** No code needs it to exist, so the deploy order does not matter, and a rollback leaves it in place harmlessly. It is a plain `CREATE INDEX IF NOT EXISTS`, which blocks writes to `job` while it builds: fine for a small table, but on a large one build it by hand with `CREATE INDEX CONCURRENTLY` first (the migration then skips it).

**Migration `0010_p4c_schedules.sql` must be applied before deploying this version.** The schedule services and the tick read what it adds to `job_schedule`: `deleted_at` and `last_manual_at` (nullable), `updated_at` (not null, default `now()`, so existing rows take the migration time) and the partial index `job_schedule_due_idx`. It is additive and guarded with `IF NOT EXISTS`; an older build ignores the new columns, so a rollback needs no down-migration (a schedule deleted in this version would look live and disarmed to the older build).

**Migration `0012_p4b2_oauth.sql` must be applied before deploying this version.** It creates the `oauth_token_cache` table: one row per outbound credential (a system credential or a type default), holding the encrypted access token fetched for an OAuth 2.0 client credential, its expiry and the refresh lease. Rotate and revoke of any outbound credential delete from it, so the table has to exist before the new code runs. It is additive and idempotent: `CREATE TABLE IF NOT EXISTS`, the constraints inside `DO` blocks that check `pg_constraint` first, and `CREATE UNIQUE INDEX IF NOT EXISTS`, so a re-run is harmless. It adds no environment variable: the cached tokens are encrypted under the existing `CREDENTIAL_MASTER_KEY`. An older build never reads the table, so rolling back leaves it in place harmlessly, but it does not know the `oauth2_client` credential type and cannot authenticate with one: hold the systems whose endpoints use one `SUSPENDED` until you roll forward.

**Migration `0013_async_inbound.sql` must be applied before deploying this version.** The inbound route and the drain read what it adds: `job.accepted_async` (boolean, not null, default `false`, so every existing job reads as not async) and the `job_payload_vault` table, which holds the encrypted executable copy of each payload accepted with 202. The vault row is keyed by the job id with a foreign key that cascades on delete, and an index on `expires_at` serves the purge. It is additive and idempotent (`IF NOT EXISTS`, and the foreign key inside a `DO` block that checks `pg_constraint` first), so a re-run is harmless. It adds no environment variable: the payloads are encrypted under a key derived from the existing `CREDENTIAL_MASTER_KEY`.

**Migration `0014_service_keys.sql` must be applied before deploying this version.** The gateway and the credential services read the `system_service_key` table it creates: one row per service key of a system (the row id is the key id, `kid`), holding the encrypted key, its expiry, revoke and rotation columns, with a foreign key to `external_system` that cascades on delete, an index on `external_system_id` and a partial unique index on `(external_system_id, label)` for live rows. It is additive and idempotent (`CREATE TABLE IF NOT EXISTS`, the foreign key inside a `DO` block that checks `pg_constraint` first, and `IF NOT EXISTS` on both indexes), so a re-run is harmless. It adds no environment variable: the keys are encrypted under a key derived from the existing `CREDENTIAL_MASTER_KEY`.

**Cutover to service keys.** From this version a system of a `partner+service` type answers `401` to every call until it holds a service key, because the global secret is no longer read. Before deploying, list the live systems of such types; right after migrating and deploying, issue a key for each on its Credentials tab and give the partner the key, its `kid` and the new mint command. A token without `kid` and `sys` is refused.

**Migration `0015_storage.sql` must be applied before deploying this version.** The object storage services read the columns it adds to `storage_config`: `endpoint` and `access_key_id` (text, not null), `force_path_style` (boolean, not null, default `true`), `created_at` and `updated_at`; it also makes `bucket` and `region` not null, adds a unique index on `external_system_id` (one store per system) and a CHECK that `provider` is `s3_compatible`, and grants the built-in `operator` role `storage:read` and `storage:write` (admin, viewer and custom roles are untouched). The new not-null columns have no default, so the table must be empty when it runs: no earlier version wrote to it, and a pre-check (`SELECT count(*) FROM storage_config`) should read 0. It is not written to be re-run by hand: the migrator applies it once and records it in the ledger. It adds no environment variable: each system's store and keys live in the database, and the secret access key is encrypted under the existing `CREDENTIAL_MASTER_KEY`.

**Rollback for 0014.** The migration only adds a table, so promoting the previous deployment back restores the old global-secret path, and the table stays in place harmlessly. An existing deployment keeps the environment it was built with, so this works even after `SERVICE_JWT_SECRET` has been removed from the production environment; a fresh build of the pre-0014 code would need that variable restored.

**Rollback for 0015.** Promoting the previous deployment back is safe: an older build never reads `storage_config`, so the new columns, index and CHECK stay in place harmlessly. The operator role keeps the two storage ids, which an older build does not know; permission checks only test membership, so they grant nothing there. Stored store configs remain and are used again on the next roll forward.

**Rollback hazard for 0013.** The table and the column stay in place after a rollback and are harmless once no async job is queued. The hazard is a job that is still queued: an older build does not know `accepted_async`, so it would run a `PENDING` or `RETRY` async job on its stored payload, which is the redacted copy, and with outbound config an inbound connector never receives. Before rolling back to a build older than 0013, drain every `accepted_async` job in `PENDING` or `RETRY` (let it run, or wait for the tick) or discard it, and only then roll back.

**Rollback hazard for 0009.** Rolling the app back to a build older than 0009 leaves the new columns and the table in place, and they are harmless there because the older build never reads them; no down-migration is needed. The hazard comes after endpoints have an auth binding: the older build ignores `auth_label` and `auth_header`, so those jobs go out without the credential and the partner answers 401 or 403 until you roll forward. The older build also does not know the `flag` credential type or the new endpoint keys, so it may fail to list or validate a flag row, and its strict import refuses a system export taken from this version (which carries `authLabel` and `authHeader` when they are set). Before rolling back, note which endpoints have an auth label (Endpoints tab) and either accept unauthenticated calls for them or hold those systems `SUSPENDED`.

```
npm run db:seed
```

This runs `db/seed.ts`, which is the platform's only seed step: it creates exactly one admin user (password hashed with bcrypt) and the three baseline roles (`admin`, `operator`, `viewer`) with their permission sets (see `core/auth/permissions.ts`), and links them. It is idempotent: running it again against a database that already has these rows does nothing destructive, it just logs that they already exist.

- Default admin email: `admin@interchange.local` (override with `SEED_ADMIN_EMAIL`).
- Admin password: `SEED_ADMIN_PASSWORD`. **It is required unless `DATABASE_URL` is a local database: the seed throws instead of using a default, in production and also against any hosted database seeded from a workstation (`NODE_ENV` is not consulted for this).** Only a `localhost` / `127.0.0.1` database, or an explicit `SEED_ALLOW_DEFAULT=1`, gets the published development default `changeme-admin-1`, which must never be used on a reachable deployment.
- Re-running the seed also resets the `operator` and `viewer` role permissions to the current catalog defaults (and migrations `0001` and `0004` add the defaults once for existing rows: `0004` only the three certificate and SFTP permissions). Edit those two roles by creating differently named roles instead.
- Partner systems, integration types, and connector instances are **not** seeded. They are registered through the admin UI after this first login, which is the intended flow: the seed only gets you into the console, everything else is configuration.

If you change `db/schema/*.ts`, generate a new migration before applying it:

```
npm run db:generate
```

This runs `drizzle-kit generate` against `drizzle.config.ts` (schema at `./db/schema/index.ts`, output to `./db/migrations`), producing a new SQL file for review before you run `db:migrate`.

## Automated deploy and the Health workflow (P7b)

P7b adds a production deploy job to the CI workflow and an hourly Health workflow. Neither adds an application environment variable or a migration. Both live in `.github/workflows/`.

### The deploy job (`.github/workflows/ci.yml`)

The `deploy` job runs only on a push to `main`, and only after the `verify` job passes (`needs: verify`, `.github/workflows/ci.yml:56-58`). A pull request never deploys. Its steps, in order:

1. **Check out** with the full history (`fetch-depth: 0`, needed by the migration gate) and `persist-credentials: false`, so the job token is not left in the git config (`.github/workflows/ci.yml:74-77`).
2. **Check secrets.** The three repository secrets `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` must be non-empty. If any is missing the job fails at once with an error that names it, before anything else runs (`.github/workflows/ci.yml:78-87`).
3. **Migration gate** (`scripts/ci/migration-gate.sh`, below).
4. **Deploy to production**: `npx --yes vercel@50.22.1 deploy --prod --yes --token="$VERCEL_TOKEN" --meta githubCommitSha="$GITHUB_SHA"` (`.github/workflows/ci.yml:92-103`). The Vercel CLI version is pinned. The token is passed with `--token` because this CLI does not read `VERCEL_TOKEN` from the environment (the first deploy run failed with "No existing credentials found" without it); the org and project ids are read from the environment. GitHub Actions masks the secret in the log, and the runner is discarded after the job. The commit is recorded on the deployment as `githubCommitSha`, which is what the next run's migration gate reads. The deployment URL and the commit go into the job summary.
5. **Health smoke** (`scripts/ci/health-check.sh`): `GET /api/health` must answer `200` with `status` and `db` both `ok`, tried 3 times 20 seconds apart (`scripts/ci/health-check.sh:1-34`, `.github/workflows/ci.yml:104-105`).

Settings that matter:

| Setting | Value | Why |
|---|---|---|
| Permissions | `contents: read` | The job needs nothing else from GitHub (`.github/workflows/ci.yml:61-62`) |
| Environment variables | `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, from repository secrets | `.github/workflows/ci.yml:69-72` |
| Timeout | 15 minutes | `.github/workflows/ci.yml:60` |
| Concurrency | group `deploy-production`, `cancel-in-progress: false` | A running deploy is never cancelled (`.github/workflows/ci.yml:63-68`) |

**Two pushes close together.** The job's concurrency group keeps one run going and at most one waiting. When a third arrives, GitHub replaces the older waiting run with the newer one, so a middle push may never deploy, but the last push always does. The workflow-level group `ci-<ref>` behaves the same for whole runs on `main` (`cancel-in-progress` is on only for pull requests, `.github/workflows/ci.yml:11-14`). A skipped middle push cannot hide a migration, because the migration gate compares against what production serves, not against the previous push.

### The migration gate

Migrations stay manual: the deploy job never touches the production database. The gate (`scripts/ci/migration-gate.sh`) makes sure a migration is not forgotten.

- **Baseline.** The commit production serves now, read from the Vercel API as the `githubCommitSha` of the production deployment (`scripts/ci/migration-gate.sh:36-47`). If that is missing or not in the history, it falls back to `github.event.before` (`scripts/ci/migration-gate.sh:49-68`). If neither is usable (first push, force push), the baseline is unknown.
- **Rule.** If `db/migrations/` changed between the baseline and the head commit, or the baseline is unknown, the head commit message must contain a line that is exactly `migration-applied`. Without it the job fails before `vercel deploy` runs, with an error that says what to do (`scripts/ci/migration-gate.sh:70-113`).
- **The marker is read from the head commit only** (`git log -1`, `scripts/ci/migration-gate.sh:71`). A migration committed earlier and not yet deployed still counts, so the commit that triggers the deploy needs the marker. A sentence such as "not migration-applied" does not count, because the whole line must match.
- **Order of work.** Apply the migration to the production database with `npm run db:migrate` (see "Migration and seed steps"), then push or amend the head commit so its message has the line `migration-applied`, then let the job deploy. If a migration needs code that is deployed first, read its note above: several migrations must be applied before the matching code ships.
- **The result is in the job summary** as a "Migration gate" block: baseline, head, reason, changed files and decision (`scripts/ci/migration-gate.sh:98-108`). The token is never printed and tracing is never enabled (`scripts/ci/migration-gate.sh:24`).

### Secrets and token rotation

The three values are plain repository secrets (Settings, Secrets and variables, Actions), not a GitHub Environment. Environments with protection rules (required reviewers, branch rules) are not available on the Free plan for private repositories, and this is a single-owner repository. The consequence: anyone with write access to the repository can read the secrets through a workflow run, so keep write access to the owner.

To set or rotate one, pipe the value on stdin so it stays out of shell history and the process list:

```
gh secret set VERCEL_TOKEN -R faizkhairi/interchange
```

After rotating the Vercel token in the Vercel account, run that command again with the new value, then revoke the old token. `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` are identifiers, not credentials, but they are stored as secrets too so one rule covers all three.

### The Health workflow (`.github/workflows/health.yml`)

Name `Health`. It runs on the cron `17 * * * *` (minute 17 of every hour, UTC) and can be started by hand (`workflow_dispatch`) (`.github/workflows/health.yml:3-6`). The job has a 5 minute timeout, a sparse checkout of `scripts/ci` only, and `persist-credentials: false` (`.github/workflows/health.yml:14-21`). It runs `scripts/ci/health-check.sh` with 3 tries 30 seconds apart (`.github/workflows/health.yml:22-26`).

The check passes only on HTTP `200` with `status` equal to `ok` and `db` equal to `ok`. It fails on a non-200 answer, a `status` that is not `ok`, or a `db` that is not `ok`, and on failure prints only the HTTP code and those two fields, never the body (`scripts/ci/health-check.sh:19-34`). A failed run shows red in the Actions tab; GitHub's notification settings decide whether anyone is emailed. GitHub may start a scheduled run late under load.

### Risks and limits

- **Actions minutes.** The hourly Health run costs about 720 minutes a month (24 runs a day, billed at least one minute each). The Free plan includes 2,000 minutes a month for private repositories. The `verify` job also costs 16 to 25 minutes per push to `main` and per pull request run, plus the deploy job. Heavy pushing plus the hourly check can reach the limit. A 2-hourly cron (`17 */2 * * *`) halves the Health cost. Check Settings, Billing, Actions usage before raising the cadence.
- **Secrets are repository secrets**, not an Environment (see above).
- **Actions are pinned by tag** (`actions/checkout@v4`, `actions/setup-node@v4`), like the rest of the workflow. A tag can move. Pinning to a full commit SHA is stronger; it is not done here.
- **No automatic rollback.** A failed Health smoke leaves the new deployment live. Roll back by promoting the previous deployment (the rollback section of the operations runbook, in the source repository); a migration is not reversed by a rollback.
- **The deploy job builds on Vercel**, so a build that passes in CI can still fail there; the job fails in that case and production keeps the previous deployment.
- **Manual deploys still work.** The job is a convenience, not a lock. A deploy made by hand with the Vercel CLI carries no `githubCommitSha` unless the command sets it, and the gate then falls back to `github.event.before` as its baseline (`scripts/ci/migration-gate.sh:59-68`).

## Activating the dormant platform for a real project

A fresh deploy, fully migrated and seeded, is intentionally inert. Nothing above makes it start accepting live partner traffic or running recurring jobs. To bring a real project online:

1. **Log into the admin console** at `/login` with the seeded admin credentials, using the password you set in `SEED_ADMIN_PASSWORD`. Then open Profile (linked beside Sign out) and change the seeded password, so it no longer exists as an environment value, and add your team under Govern, Users. A new user gets a one-time 20-character temporary password shown once; pass it on securely, because there is no email service and no forced change at first sign-in. Set a strong `SEED_ADMIN_PASSWORD` at seed time anyway.
2. **Register an `integration_type`** for each kind of connector you plan to use, pointing its `handler_key` at an existing entry in the generated manifest (see `docs/connectors.md` if you need to add a new connector type first).
3. **Register the partner as an `external_system`.** It is created with `status = 'SETUP'` by default; it will not accept any inbound traffic yet, even if you go on to issue it credentials in the next step. This is deliberate: you can fully provision a partner (endpoint config, credentials) before exposing it to any traffic.
4. **Issue credentials** from the system's detail page (click its code in the Systems list, then open the Credentials tab). For an inbound partner, issue an API key, a bearer token or Basic credentials (you choose the username, the server generates the password), optionally with a label and an expiry in days. For a system of a `partner+service` type, also choose Issue service key: the key and its key id are shown once, and without a usable key every call to that system is a 401. The secret is shown once; store it wherever the partner configures their outgoing calls. Use Rotate to replace one (an optional grace period of 0 to 1440 minutes lets the partner switch over; the default 0 revokes the old credential immediately) and Revoke to end one. For an outbound partner, configure its endpoint (`endpoint_config`: base URL, path template, method, timeout, retries) and store any credentials it needs to call out with Store credential on the same tab (`system_credential`, encrypted immediately via the vault). Revealing a stored outbound secret stays off unless `CREDENTIALS_REVEAL_ENABLED=1` and the user holds `credentials:reveal`. An outbound credential has a type: `api_key`, `oauth2` (a static bearer token), `oauth2_client` (OAuth 2.0 client credentials: the form takes the token URL, client id, client secret and an optional scope, audience and auth method, and the platform fetches and caches the token itself), `basic` (one secret in the form `user:password`) or `flag` (a secret on/off switch a connector reads). Except for a flag, it also has a list of allowed origins (1 to 10 exact origins, set at store or when rotating with a new secret): the credential is sent only on a request whose origin is both the endpoint's base URL origin and in that list, so enter the base URL origin there. An `oauth2_client` credential must have the list, and it must also contain the token URL's origin. To make an endpoint send a credential, set its Auth credential label (and, for an API key, the header, default `X-API-Key`) on the Endpoints tab. A label with no active credential dead-letters the job at attempt 1 as `CREDENTIAL_MISSING`; a stored credential that does not decrypt (usually a `CREDENTIAL_MASTER_KEY` that does not match) or cannot be a header value does so as `CREDENTIAL_INVALID`, and DLQ replay recovers the jobs once it is fixed.
5. **Flip the system to `ACTIVE`.** Only after this does `authenticatePartner()` accept traffic for that system's `systemCode`. This is the single switch that turns a fully configured but dormant partner into a live one.
6. **If you need recurring outbound work, arm the tick and a schedule.** Create a schedule with `schedules.create` (system, cron expression in UTC, payload; the handler is the system's integration type handler) and set `QSTASH_TOKEN`, `APP_URL`, `QSTASH_CURRENT_SIGNING_KEY` and `QSTASH_NEXT_SIGNING_KEY` in your environment. On the Schedules page, "Arm tick" registers the one QStash schedule (cadence `QSTASH_TICK_CRON`, default every 5 minutes) that calls `POST /api/jobs/tick`; arming an individual schedule only enables it and sets its `next_run_at`, it registers nothing with QStash. Nothing fires until the tick is armed. Each tick, in order: reclaims jobs stuck in `PROCESSING` (older than `JOB_STUCK_MINUTES`), fires the schedules whose `next_run_at` is due (claimed by compare-and-swap, so overlapping ticks fire a schedule once) and advances `next_run_at` from the cron expression, drains a bounded batch of `PENDING`/`RETRY` jobs, and prunes expired rate-limit buckets and old `activity_log` rows, then prunes old jobs, resolved alerts and old notifications, probes up to 5 due health URLs (`healthChecks`, P7b) and runs the throttled alert evaluation, which posts new alert transitions to the alert webhook when one is set (each stage is isolated; a failed stage makes the tick answer 500 so QStash retries). `/api/jobs/dispatch` (enqueue due schedules only) and `/api/jobs/process` (drain only) remain available as narrower endpoints. All three reject unsigned requests (401) and answer 503 while the signing keys are unset. Until `QSTASH_TOKEN` is set, `armTick()` in `core/jobs/qstash.ts` is a documented no-op, so nothing fires on a timer by accident. Check your QStash plan's message quota before lowering `QSTASH_TICK_CRON`; the quota is spent per tick, not per schedule, and a 5-minute cadence is a safe default.
7. **Verify with the health endpoint.** `GET /api/health` returns the service name, `status`, the connector count, a database reachability check (`db`) and a timestamp, useful as a first smoke test after each of the steps above, and as an ongoing liveness probe for uptime monitoring afterward.

None of steps 2 to 6 require a redeploy. They are all admin-console or QStash-dashboard actions against the already-deployed platform.

**With the tick dormant.** Without an armed QStash tick, alerts and retention still run, only less often: a throttled alert evaluation (at most once per 5 minutes across instances) is triggered after console reads and after inbound calls finish, and retention is triggered the same way. Alerts are therefore only as fresh as the traffic that triggers them: with no console use and no inbound calls, nothing evaluates until someone opens the console or the tick is armed. The same holds for the drain: with the tick dormant, due jobs are drained by the throttled after-response drain, and a call accepted with 202 runs its own job right after the response, so async inbound works without a tick (only its retries wait for the next drain window). Scheduled health checks (P7b) follow the same rule: with the tick dormant, a health URL is probed only after the response of a System health read (at most once per 15 minutes, 3 systems), so nothing is probed while nobody opens that page; once the tick is armed, its `healthChecks` stage probes up to 5 systems every 240 seconds at the most ([alerting.md](alerting.md#scheduled-health-checks-a10)). The `tick_stale` rule stays quiet while the tick is not armed, and the System health page and the admin "Evaluate now" action work either way. The arming steps above are unchanged.

**Sessions started before an upgrade to P3c.** The console reads permissions from the session token (8 hour lifetime), so an operator or viewer who was signed in before the release does not see the bell, the Notifications page or System health until the next login. The server already accepts the calls, so nothing else is needed: ask them to sign in again.

**Ending sessions (P5a).** To force a user out, open Govern, Users and choose Sign out everywhere, or Disable, or Reset password on their row; each ends every session of that user at their next request. P5a needs no migration, no new environment variable and no seed change: the seed still restores the built-in roles `admin`, `operator` and `viewer` on every run, which is why they are read-only in the console (make a custom role from a built-in with Duplicate). The last active superadmin cannot be disabled or demoted, so the console cannot lock itself out through the UI; nobody can reset their own password through Users (they use Profile), so a lost password of the only superadmin has no console remedy. Keep a second superadmin account, which can reset the first.

## Operating registry entries

**Edit and configure.** A system's detail page has tabs for Overview (rename, request limit, delete), Credentials, Endpoints, CORS and Health. The Endpoints tab holds the outbound endpoint config (base URL, path template, method, timeout, retries, and the Auth credential label and API key header) and the per-endpoint limits; a base URL that points at a private or reserved address is refused with a field error. Remember that declaring any endpoint limit turns the list into the system's endpoint allowlist, so list every endpoint the partner calls. The CORS tab takes one origin per line.

**Health check.** Set a health URL on the Health tab and use "Check now". The platform sends a `GET` with a 5 second timeout through the outbound guard and stores `UP` or `DOWN` with a short reason (`BLOCKED`, `DNS`, `DNS_TEMPORARY`, `TIMEOUT`, `HTTP_503` and so on), never the upstream response. `DNS_TEMPORARY` means a temporary resolver failure: press "Check now" again. Changing the URL resets the status to `UNKNOWN`. The dashboard's "Health failing" card links to the list filtered to `DOWN` systems.

**Export, import and duplicate.** Export a system from the Systems list to get a JSON document of its configuration. It contains no credentials of any kind, and `endpointConfig.settings` is exported as stored, so keep secrets out of that map. Import on the same page (paste the JSON or pick a file) creates the system in `SETUP`; duplicate does the same inside the platform from an existing system. In both cases issue credentials afterward and set the system `ACTIVE` when it is ready. To move a system between environments, export it from one, import it in the other, and issue fresh credentials there: the integration type is matched by its code, so register that type in the target first.

**Default credentials of an integration type.** On the Catalog page, the Default credentials button on a live type opens a dialog to store, rotate, revoke and reveal credentials that every system of the type inherits. A system's own active credential with the same label wins; the system's Credentials tab lists the type's rows under "Inherited from type" and marks a shadowed one "Overridden". A store, rotation or revoke, and a type delete or restore, applies from the next job: each instance keeps decrypted values in memory for at most 300 seconds and re-reads them as soon as a version counter changes, so no restart or redeploy is needed. A job already running finishes with the value it had.

**Delete and restore.** Deleting a system suspends it and removes it from the lists; the Systems list has a Deleted tab with Restore. Restore always leaves the system `SUSPENDED`, so set it `ACTIVE` deliberately. Queued jobs of a suspended system wait (they are held, not failed) and run once it is `ACTIVE`; queued jobs of a deleted system fail without retry. Integration types delete and restore the same way, and a type cannot be deleted while a non-deleted system uses it.

**Freeing a deleted code.** Deleted system codes and integration type codes stay reserved, so creating, importing or duplicating with one is refused with "system code already exists (deleted)". There is no purge. To use that code again, restore the deleted row (Deleted tab, Restore): the code continues as the same system, with its history, and you edit it from there. A different partner needs a new code. The reservation exists so that old credentials, jobs and audit history can never attach to a different partner.

## Cost profile

Because the platform is dormant by default and stays dormant until explicitly activated, an unconfigured or lightly used deployment has close to zero idle cost:

- Neon's serverless Postgres scales to near-zero compute when idle, and the free tier covers a project's own schema comfortably at this size (31 core tables plus the opt-in upstream table).
- Vercel's serverless functions only run (and only bill) when a request actually arrives; there is no long-running worker process consuming compute between requests.
- No QStash schedule exists, and therefore no timer tick runs and nothing recurring is billed, until a project explicitly arms one. A dormant deploy still has the throttled after-response drain: at most once per 60 seconds it reclaims stuck jobs and drains up to 3 due jobs (stopping 15 seconds in), triggered by console reads and by authenticated inbound calls answered under 400. With an empty queue it only writes its `drain_last_run` stamp; it writes a `process_log` row only when it did work. It makes outbound calls only for jobs that are already queued, so it adds function time only where there is work.

**Function duration.** Four routes declare `export const maxDuration = 60` (seconds): the admin catch-all (`src/app/api/admin/[...path]/route.ts`), inbound (`src/app/api/inbound/[systemCode]/[endpoint]/route.ts`), tick (`src/app/api/jobs/tick/route.ts`) and process (`src/app/api/jobs/process/route.ts`). The after-response drain runs inside the admin and inbound functions, and its 15 second claim budget plus one connector timeout (30 seconds at most) stays under that limit. An inbound call accepted with 202 runs only its own job after the response, so its bound is one connector timeout (30 seconds at most). Check that your Vercel plan allows a 60 second function; if it caps lower, lower `DRAIN_BUDGET_MS` and `DRAIN_AFTER_LIMIT` in `core/jobs/drain.ts` before deploying. Migration `0008` is additive and nullable, so the previous deployment stays compatible: roll back by redeploying or re-aliasing the previous build, with no down-migration. Migration `0009` is additive too, but read its rollback hazard above before rolling back past it.

This makes the free tier of each service viable for evaluating the platform or running a small number of low-volume partners, with cost scaling up only as real traffic and armed schedules are added, not as a fixed baseline.
